### Firebase 版の複数所属・削除（2026-10-24、Issue #24）

当初は Firebase 版を単一所属に限定していたが、Issue #24 で以下に変更する。

- `users/{uid}.teamIds` を所属の索引、`teamId` を選択中のチームとする。旧プロフィールはログイン時に既存の `teamId` を配列へ移行する。アカウント名を維持し、チーム内の名前は `members/{uid}.displayName` に保存する。
- 所属は最大20チーム。常時取得するチーム概要とプロフィールの増大を抑えるための上限で、チームのメンバー数の制限ではない。参加・離脱は配列の差分と `members` の変更をルールで同時検証する。
- `membershipChangeTeamId` は所属を変更した対象チーム。管理者による除名・削除は選択中のチームに限定するため、リポジトリが先に対象チームを選択する。他人の所属一覧のうち対象外の要素・アカウント名・対象外の選択状態は変更できない。
- チーム削除は `deletionUid` に開始者のUIDを保存する。**削除中も既存メンバーは通常どおり使え、所属が変わるのは管理者が削除を最後まで完了したときだけ**とする（2026-10-24、PR #27 のレビューで変更）。削除中に止めるのは新規参加と参加コードの発行のみ。清掃（無条件の削除）は開始者だけが行える。取り消しは設けない。
  - 理由：開始した管理者が途中で止めたまま戻らなくても、ほかのメンバーが閉じ込められないようにするため。削除中の画面は開始者にだけ表示する
  - 用具は、通常の削除と同じく所持数（`heldCount`）を更新しながら1点ずつ消す。途中で止まっても所持数と実際の用具が食い違わず、メンバーは通常どおり離脱できる
  - 清掃と並行してメンバーが予定・メモ・用具を追加した場合、最後の確認より後に追加された分は親の削除後も残ることがある（参照できないデータとして保存容量だけを使う）
- メモを100件単位で削除してから親の予定を削除し、用具・用具名予約・参加コード・非公開コードを清掃する。メンバーは1人ずつ所属更新とメンバー削除をトランザクションで処理する。削除者自身の所属・メンバー・チーム親は最後に同時削除する。これにより途中失敗・再読み込み後も削除者の画面から再開できる。自動再試行の無限ループやバックグラウンドの定期処理は作らない。
- 予定単体の削除も `deleting: true` で新規メモを止め、メモの清掃完了後に親を消す。途中でチーム削除へ進んでもメモの探索先が残る。旧版ですでに親が消えて残った孤立メモについては、既知の予定IDによる再実行またはコンソールでの清掃が必要（Web SDKはサブコレクションの親ID一覧を列挙できない）。
- これは権限を持つ管理者による段階的な削除で、全体を1トランザクションにはしない。クライアントが停止した場合は自動完了せず、ルールもサブコレクションの全件清掃を列挙検証するものではない。削除者が再開する運用とする。Cloud Functions・Blazeは使わない。

### 複数チーム所属への変更（2026-10-24）

ユーザー要望により単一所属の制約を廃止する。所属一覧は `teamIds`、現在選択中のチームは `teamId` に保存する。参加・作成時にチーム内の名前を必須入力し、変更はそのチームのメンバー情報と保有用具に限定する。アカウント登録時の名前はアカウント名として保持する。離脱・登録削除は対象チームだけに適用する。今回の実装はモックで、Firestore 実装時もルールによるチーム単位の権限強制を維持する。

### チーム削除・コピー互換性（2026-10-24）

ユーザー要望により管理者がチーム全体を削除できるようにする。最後の管理者も削除できるが、全メンバーに影響し元に戻せないことを確認画面に明示する。対象チームのデータとコードを削除し、全員の所属一覧・選択状態を一度に更新する。今回の実装は localStorage モック。Firestore への実装ではサブコレクションが親削除だけでは消えないため、無料枠の範囲で削除処理と権限ルールを別途設計する。

参加コードのコピーは Clipboard API を優先し、HTTP や権限拒否時には選択テキストのコピーへフォールバックする。自動コピーが拒否されても、読み取り専用のコード欄で選択・長押しによる手動コピーを可能にする。

## 再取得時の権限エラーからの復旧（#94）

iPhone で、ページ再読み込み・画面内の再取得時にデータ表示と権限エラーが併存するとの報告がある。Firestore はキャッシュを先に通知するため、表示だけではサーバー取得成功と判断できない。実機での原因は未確定。

ドキュメント・一覧の購読が `permission-denied` で終了した場合、同じログインユーザーの ID トークンを強制更新し、購読を一度だけ再開する。再び拒否された場合は従来どおりエラーと空値を通知する。成功通知で再試行回数をリセットせず、実際の権限不足を隠さない。解除・ユーザー変更後は再開しない。セキュリティルールは変更しない。

通常時の購読数は変えず、拒否された購読に限り再接続を最大1回追加する（追加の読み取り・ルール評価が発生し得る）。参加コードの購読は管理者権限変更時の既存の扱いを維持する。実機で改善しない場合は、発生タブ・ブラウザ・ログイン方法と拒否された購読先を確認し、キャッシュ内の旧所属などを追加調査する。

## 無効な所属索引の自動修復（#97）

本番の読み取り調査で、プロフィールの `teamIds` にチーム本体・本人メンバー情報の両方が存在しないIDが残っていることを確認した。正常なチームは表示できる一方、残存IDの購読が権限拒否となる。不整合を生んだ操作履歴は保存されておらず、発生経路は断定できない。現行の削除・離脱・除名はプロフィール更新とメンバー削除を同一トランザクションで行っており、この整合性は既存の統合テストでも確認する。

チーム配下のドキュメント・一覧の購読が権限拒否で終了した場合、#94 の再認証後の再試行に続いて、自分のプロフィールから対象IDだけを外すトランザクションを試みる。削除可否は既存の `users/{uid}` の `removal()` ルールが本人メンバーの不存在をサーバーで確認する。キャッシュやエラーの種類だけを根拠に削除しない。ルール変更・管理者SDK・Cloud Functions は不要。

選択中のIDを外すときは残りの先頭へ切り替え、残りがなければ未所属に戻す。残りにも無効なIDがあれば購読時に同じ処理で整理する。正常な所属の読み書き権限は変えない。本人のメンバーが存在する場合や通信失敗で修復が拒否された場合は、元の購読エラーを通知する。

同一アカウント・チームの同時エラーは1つの修復処理にまとめる。修復済みのIDはリポジトリ内で記録し、旧購読の後発エラーに対する重複通知を避ける（再加入後にプロフィールにIDが戻っていれば、改めてサーバーのルールで検証する）。購読解除後の結果通知は破棄し、ユーザー変更後に修復を開始しない。本番個別データの管理者修正は行わず、更新版のアプリから一般ユーザー自身の権限で復旧できるようにする。

## P2 の設定機能（#45・#66・#68・#100）

- よく使う場所は `settings.places?: string[]` に順序付きで最大20件・各100文字を保存する。未設定は空一覧とみなし既存データを移行しない。SDKで前後空白を除去し、空欄・重複を拒否する。ルールでも型・件数・文字数・重複・管理者権限を検証する。予定の `place` は選択時の文字列のまま保存し、候補の変更で過去の予定を変更しない。自由入力・毎週の一括登録でも使える。
- アカウント名は `users.displayName` を正本とする。チームの `members.displayName`、用具の `holderName`、Google 側の名前を変更しない。未所属でもアカウント設定に入れる。
- パスワード再設定はログイン中のメール宛てに既存の Firebase 再設定メールを送る。Google のパスワードは変更しない。
- アカウント削除は2段階（影響の確認 → 「削除」の入力と再認証）。メール利用者は現在のパスワード、Google利用者はポップアップ、両方ある場合は選択する。LINE内などではGoogle再認証を外部ブラウザへ案内する。
- 全所属で最後の管理者でないことを先に確認し、`users.deletingAccount = true` を保存する。この間はルールで新規参加・作成と用具の新規取得を止め、用具解放 → 所属解除 → プロフィール削除 → Auth削除の順に進める。所属解除は既存のトランザクションを再利用し、同時変更もルールで検証する。プロフィール削除は本人・未所属・削除フラグ・直近5分の認証を必須とする。
- 途中失敗では解除済みの所属を戻さず、設定画面から再認証して再開する。削除フラグを本人が解除して中断することもでき、管理者変更などを済ませてから再実行できる（解除済みの所属は戻さない）。プロフィール削除後にAuth削除だけ失敗した場合も再実行できる。再ログインで空プロフィールが再作成された場合も同様。Authの直接削除APIをクライアントのFirestoreルールで制限することはできないため、チーム整理の保証はアプリの削除手順について検証する（サーバーやCloud Functionsは追加しない）。
- アプリの Auth 言語は日本語に固定。2026-10-26、本番の既定言語 `ja` と、確認・再設定メールの差出人 `BUKATSU` を管理APIで設定し読み戻した。プロジェクト表示名も `BUKATSU` と確認済み。独自の件名・本文変更は `EMAIL_TEMPLATE_UPDATE_NOT_ALLOWED` で拒否されたため、Firebase既定の日本語テンプレートを採用する。メールの実配送と確認完了画面の実機確認は未実施。

最終検証で、複数の無効所属が同じプロフィールを並行更新すると、ルールが最新値に対して「対象1件だけの削除」を検証して一方を拒否する競合も再現した。所属修復をリポジトリ内で直列化し、同一チームの重複要求は従来どおり共有する。追加の権限緩和は行わない。

## 大量データ検証の範囲（#69）

通常規模と100人・500予定・10万メモ・300用具を、専用プロジェクトのエミュレータで検証する。投入・計測はTypeScript、通常テストでは負荷試験をスキップし、本番やCLI管理認証を使わない。実際のリポジトリとルールを使って削除・再開を確認し、量に応じたUIの取得制限やデータ構造の変更はこの検証に混ぜない。判明した全件取得の読み取り超過、大量削除の日次上限、回答100件境界は #103・#104・#105 で個別に扱う。測定環境と課金の下限・未確認事項は `docs/performance/issue-69.md` に記録する。


## P2 大量データの改善（#103・#104・#105）

- 予定一覧は初回20件＋次ページ有無の確認用1件。追加表示で20件ずつ取得範囲を広げ、取得済み範囲を1つのリスナーで購読し直す。カーソルでページを固定しないため、日付変更・追加・編集による並び替えにも追従する。全件表示を選べば読み取りとDOMは増える。詳細・編集は予定IDの独立した購読を使い、表示範囲外・過去へ移動しても編集結果を表示する。再取得では表示件数を保持し、タブを開き直す・チーム切替で20件へ戻る。
- チーム削除の事前集計は予定・用具・メンバーの最低件数だけ（メモ・用具名等は含まない）。全メモを見積もりのために読み取らない。最低件数を総数や完了率と呼ばず、削除中は今回の実行で成功した削除操作数と段階を表示する。累計は永続化せず、再読み込み後は不明と表示。進捗を保存するための課金書き込みは増やさない。
- 1回の削除実行は1000件で停止し、利用者が確認して再開する。端末やタブをまたぐ日次上限の強制ではなく、プロジェクト全体の残量も保証しない。停止要求は処理の区切りで確認し、送信済みの処理は取り消さない。quotaエラー時は自動の清掃再試行をせず、使用量確認と日次リセット（太平洋時間午前0時ごろ）を案内する。メモ等の清掃はオフライン書き込みキューへ積むバッチから最大1試行のトランザクションへ変更。親と削除開始者を最後まで残す再開方式は維持する。
- 出欠の出席以外の保存上限を100から500件/予定へ拡張する。チーム参加人数そのものの上限ではない。既存mapを保ちデータ移行不要とし、参加時にも回答数の制約を案内する。450件から残量を表示し、新しいキーを500件超へ増やす操作は最新の予定を読むトランザクションで専用エラーにする。既存回答の変更・出席に戻す操作は可能。最新の件数を検証するため、オフラインでは出欠の変更を保存せず接続後の再操作を案内する。ルールも500を強制し、自分以外の回答変更は引き続き拒否する。
- 500件のキーが各128文字かつ最大4byte/文字でも、キーだけで約256KB。短い状態値と既存の制限済みフィールドを加えても1MiBに余裕を残す。回答の全件分離は予定一覧の読み取りを増やすため今回行わない。500人を超える全員が出席以外を回答する運用には別設計が必要。
