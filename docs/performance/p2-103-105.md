## 予定の取得・描画（#103）

初回表示は20件、次の有無を知るためFirestoreクエリは21件。追加表示は40件＋1件、60件＋1件と取得範囲を広げる。表示範囲の変更は単一リスナーの張り直しであり、すべてを表示すると負荷は増える。新規作成直後や編集で一覧外へ移動した予定は、予定IDの単独購読で詳細・編集へ反映する。

Mac Safariの開発ビルド（同一端末エミュレータ、500予定・100メンバー・300用具）：

| 指標 | #69 の全件表示 | 修正後 |
| --- | --- | --- |
| 最初のカード数 | 500 | 20 |
| 最初のDOM数 | 10,559 | 472 |
| 表示する予定のJSON UTF-8長 | 3,291,891B | 131,651B |
| 初期表示完了（単発） | 32,038ms | 1,673ms、再読込168ms |
| React最大commit | 45ms | 9ms、再読込8ms |

ウォームアップや通信状態が同じではなく、平均・p95・本番の保証値ではない。修正後の初回の予定SDKコールバックは57ms、再読込時36msだった。表示完了には認証復元・プロフィール・所属の購読等も含まれ、差分をReactだけに帰属しない。

追加表示では先にキャッシュの21件が通知され、後からサーバーの40件になる場面を観測した。ブラウザ計測を初回と最新の両通知を表示する方式に変更し、再測定では初回6ms・40件受信73ms・JSON263,311B・DOM892。初回コールバックをサーバー取得完了とは呼ばない。初回の追加表示で発生した待ちの正確な時間・通信層の原因は未特定であり、Safariの遅延すべてを解消したとはしない。

一覧スクロール・追加表示、再取得で40件を保持すること、用具から予定へ戻ると20件へ戻ることを実操作で確認。取得範囲の広がる間も既存カードを保持する。予定タブへの復帰は39ms、SDK初回通知9ms、DOM472だった。チーム切替はTeamSessionのkeyで状態を作り直す。既存の日付境界でのクエリ再作成と再取得の仕組みを維持する。日付を過去・遠い将来へ動かした際のIDによる取得は統合テストで確認した。

再現は `npm run scale:check` のexportを読み戻し、従来の `tests/browser/scale.html` を開く（詳細は [#69の手順](issue-69.md)）。初期のSDK計測は購読から通知までの経過時間で、キャッシュ・認証・SDK・ローカル通信を含み、ネットワーク時間単独ではない。

## 削除の停止・再開（#104）

事前見積もりは3本のcount集計（予定・用具・メンバー）と親1件の最低値。メモ等を含む総数や残り時間・完了率を表示しない。1回1000削除操作まで、手動停止は処理の区切りで受け付ける。今回の成功分だけを進捗として通知し、再読み込み後の累計は不明と明記する。Firestoreへの進捗保存は増やさない。

通常の統合テストで、2操作の小さな予算で停止→親と開始者が残る→未削除のメモ3件が残る→別Repositoryで他チームを利用→削除再開・完了と他チーム所属保持を確認した。

負荷試験では、メモ清掃トランザクションへresource-exhaustedを注入し、再試行で成功させず停止すること、5メモが残ること、新しいRepositoryの手動操作で再開できることを確認した。実際に本番の日次枠を枯渇させたものではない。

10万メモの削除通し試験では、試験だけmaxDeletesを200000へ明示的に上げて再開を完走。再開部分は490,284ms（約8.2分）、試験全体は504.27秒。従来の約3分から遅くなった。清掃をオフライン書き込みキューへ積むbatchから最大1試行のtransactionへ変えた影響を含む。通常UIはこの上書きを使わず1000件ごとに停止する。各メンバーの他チーム所属、削除後の残存なし、所持数の整合性は維持した。

これは端末操作の安全な区切りであり、日次予算の予約ではない。別端末・別チーム・他の操作も無料枠を共有するため、管理者が使用量を確認する必要がある。quota・通信・権限の案内を分け、quota時は手動確認までアプリの清掃ループを再開しない。

## 出欠の境界（#105）

通常参加で101人目が参加し、101件目の出席以外の回答も保存できるようになった。500件で新規キーを追加する場合は容量専用エラー。既存キーの回答変更、出席に戻した後の新規回答は可能。同時に499→500件を狙った2人のうち1人だけが成功すること、直接SDKの501件目・他人の回答変更の拒否を確認した。

500キーを各128文字にしたfixtureのJSON長は300KB未満（ASCIIの場合）。最大4byte/文字の上界と既存フィールドの入力制限も含めて1MiBへ余裕を残す方針。参加人数そのものの上限は新設せず、「1予定の出席以外の回答が500件まで」を参加時と上限付近で案内する。500を超える非出席回答が必要な運用は別設計が必要。
