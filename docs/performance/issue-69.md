# 大量データ検証（#69、2026-10-26）

## 結果

現在の実装は、専用エミュレータ上で100人・500予定・10万メモ・300用具の取得と削除を完走した。100点を所持するメンバーの除名、1,001メモの予定削除と応答喪失後の再開、チーム削除の再開、他チームの所属保持、削除後のメモの残存なしを確認した。

ただし、この規模をFirebase Sparkの1日分の無料枠内で運用できるという結果ではない。全件取得と大量削除は無料枠を超える。さらに101人目の回答で、所属人数と出欠マップ上限が一致しない問題を再現した。改善は #103・#104・#105 で追跡する。本PRは検証用スクリプト・テスト・記録のみで、製品の取得件数やルールを変更しない。

## 条件と再現方法

- Node.js v24.19.0 / macOS arm64、同一端末のAuth・Firestoreエミュレータ。ネットワーク往復、データ投入後のJVMキャッシュ、SDK計測処理を含む単発値。平均・p95・本番レイテンシーではない。
- `demo-bukatsu-scale` 固定。Firestore18080、Auth19099、loopbackのみ。CLI認証・本番の環境変数・実アカウントは使わない。
- 通常：50メンバー・20予定・各20メモ・30用具。大規模：100メンバー・500予定・各200メモ・300用具。
- 本人認証がある架空ユーザーは管理者とメンバーの2人。他のメンバーは架空のUIDを持つデータであり、100クライアントの同時接続テストではない。架空UIDは約50文字で、実際のAuth UID長や回答数によってデータ量は変わる。
- 主チーム以外に同じメンバーの確認用チームを用意し、削除対象外の所属・プロフィールが保持されることを確認する。所持数は大規模で管理者100点・除名対象100点・空き100点。
- メモ本文は短い連絡文。2,000文字の最大長や非常に長いチーム名などの上限を網羅した容量試験ではない。

```sh
# Node.js 24、Java 21以上。ローカル専用エミュレータを起動して検証後に停止する
npm run scale:check

# 画面の確認を続ける場合（検証結果のexportを読み戻す）
npx firebase emulators:start --config firebase.scale.json --only auth,firestore \
  --project demo-bukatsu-scale --import=.scale-artifacts/emulator
# 別ターミナルで開発サーバー。未使用のデフォルト接続も本番へ向かないようエミュレータ指定
VITE_DATA_BACKEND=firebase VITE_USE_EMULATOR=true npm run dev -- --host 127.0.0.1 --port 5178
# http://127.0.0.1:5178/tests/browser/scale.html
```

投入だけなら、同じ専用エミュレータを起動して `npm run scale:seed -- large`。通常規模は `demo`。出力先は `.scale-artifacts/`（git管理外）。専用プロジェクトに新しいIDで追加するため、既存チームを上書きしない。手動で繰り返したデータはローカルに蓄積する。

## 削除・整合性

| 操作 | 時間 | SDK明示読み取り / TX読み取り | 更新 / 削除 | 成功バッチ最大件数 |
| --- | --- | --- | --- | --- |
| 通常チーム削除 | 1,350.7ms | 524 / 101 | 72 / 533 | 20 |
| 100点所持メンバーの除名 | 776.6ms | 202 / 303 | 202 / 1 | TXごと |
| 予定削除の再開（残り551メモ） | 938.4ms | 555 / 0 | 1 / 552 | 450 |
| 大規模チーム削除の再開 | 177,886.4ms | 101,101 / 500 | 200 / 100,901 | 100 |

「SDK明示読み取り」はgetDoc/getDocsで返された件数（空クエリは最低1件として計上）。TX読み取りはトランザクション内のget呼び出し回数。ルールの依存読み取り・再接続・インデックス読み取りなどを含む請求測定ではない。更新/削除は成功したSDK書き込み。計測外の整合性確認・fixture投入は除外している。

予定の削除では先頭予定のメモを200から1,001に増やし、最初の450件のcommit成功直後にエラーを返した。親に削除フラグと551件が残ることを確認し、新しいリポジトリで再開した。

チーム削除はさらに100メモのcommit成功直後に中断。削除開始者と親が残ることを確認してから別リポジトリで再開した。表の100,901削除は再開部分のみで、中断前の書き込みや、その前の除名・予定削除を含まない。全終了後にメモのcollection groupが空であること、対象の予定・用具・予約・メンバー・コード・親が消えたこと、全員の確認用チーム所属と選択先が保持されたことを検証した。単なる再呼び出しだけでなく、リポジトリを作り直しても再開できた。

中断はcommit応答喪失の模擬であり、実ブラウザ終了・回線切断・本番クォータ枯渇の再現ではない。

## Mac Safariでの画面確認

検証専用ページが実際の `App` をエミュレータへ接続し、React ProfilerとDOM数を表示する。開発ビルド・デスクトップSafariで、予定/用具/設定の表示・切り替えと一覧スクロールを操作した。ブラウザ用大規模fixtureは500予定・300用具・100メンバー、表示する先頭予定だけ200メモ（他の予定は0メモ）。バックエンド試験の10万メモとは別で、一覧の描画条件は同じ。

| 条件 | 表示完了まで | React最大commit | DOM要素数 |
| --- | --- | --- | --- |
| 通常・予定初期表示 | 112ms | 7ms | 476 |
| 通常・用具タブ | 71ms | 8ms | 315 |
| 大規模・予定初期表示 | 32,038ms | 45ms | 10,559 |
| 大規模・用具タブ | 30,184ms | 15ms | 2,745 |
| 大規模・設定タブ | 62ms | 11ms | 931 |

大規模ではフレーム間隔の最大136msも観測した（通常52ms）。表示完了は初期描画またはタブ押下後、main内の読み込み表示が消えた最初のrequestAnimationFrameまで。設定タブの値はメンバー等が取得済みの状態であり、同じキャッシュ条件ではない。通信待ち・ブラウザ状態・検証UI・開発モードの影響を含み、30秒の差をReactだけの問題と断定しない。Nodeの単体購読との差は未特定で、#103の再計測対象とする。iPhoneでのスクロール性能、低速回線、100人同時利用、製品ビルドの実測は未実施。

## 用具所持中のメンバー削除の再開

100点を所持するメンバーの削除でも、50点目の返却トランザクションがサーバーで成功した直後に応答を失う障害を注入した。720msで停止し、メンバーの所持数50・未返却50点・所属情報が残ることを確認。新しいRepositoryで再開し535msで残り50点の返却とメンバー削除が完了した。他チームの所属は保持され、用具の所持者も残らなかった。これは上記通し試験とは別実行の実測値であり、通信断中にSDK自身が待機し続ける挙動や端末強制終了は再現していない。

## 100件の回答境界

別の小さなfixtureで、100人分の欠席が保存済みのチームへ、確認済みの新規ユーザーが通常のコードで101人目として参加できることを確認した。そのユーザーの遅刻回答は権限エラーで拒否された。既存1人を出席にして回答キーを1つ外すと、新規ユーザーの遅刻回答が成功した。

`attendance.size() <= 100` と参加人数の無制限が一致していない。出席は保存されないため、101人いるだけで必ず失敗するのではなく、出席以外の保存済み回答キーが100件のときに起こる。#105へ切り出した。

## 無料枠の評価

[Firebaseの無料枠](https://firebase.google.com/docs/firestore/quotas)は読み取り50,000/日、書き込み20,000/日、削除20,000/日。[課金の説明](https://firebase.google.com/docs/firestore/pricing)ではルール依存や再接続の読み取りも必要であり、キャッシュがあるだけでゼロとは限らない。

| 条件 | ドキュメント読み取りの下限 | 仮定した1日の回数 | 下限の合計 |
| --- | --- | --- | --- |
| 通常規模で3タブ一巡 | プロフィール1＋チーム1＋50＋20＋30 = 102 | 50人×6 | 30,600 |
| 大規模で3タブ一巡 | 1＋1＋100＋500＋300 = 902 | 100人×6 | 541,200 |
| 大規模で予定タブだけ | 1＋1＋100＋500 = 602 | 100人×6 | 361,200 |

いずれも所属チーム概要の追加購読・ルール依存・メモ・更新通知・再試行等を除いた下限である。大規模で3タブ一巡を1人1回行うだけでも90,200読み取りとなり、無料枠を超える。従来の「50人/20予定/30用具」のデモ想定と大規模運用は分けて扱うべきで、直近件数やページ分割の検討が必要（#103）。

大規模fixtureの主チームだけで101,203ドキュメントを削除する必要がある。1日20,000削除、他の削除がゼロでも最低6日分となる。100件バッチへ分割できることと、1日の無料枠に収まることは別である。実プロジェクトへ大量データを入れて確認せず、進捗・停止・翌日再開の案内を #104 で扱う。

## 最終確認

追加の中断テストと参加コード残存チェックを含む最終状態で、空の専用エミュレータへ再投入し、負荷試験3件がすべて成功した（196.43秒）。大規模チーム削除の再開は183,202ms。通常テストは123件成功・負荷試験3件スキップ。型チェック・lint・通常/Firebase構成のビルドも成功。上記の表は初回計測値を保持し、最終再実行の値は別ファイルに保存する。既存の開発環境との衝突を避けるため、最終実行だけポートをFirestore38080/Auth39099等へ変更した。
