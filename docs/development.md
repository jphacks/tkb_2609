# 開発環境

## 起動

```sh
npm install
npm run dev      # 開発サーバー（http://localhost:5173）
npm run build    # 型チェック + 本番ビルド
npm run lint     # oxlint
```

スマホ実機で確認するときは `npm run dev -- --host` で起動し、同じ Wi-Fi から PC の IP アドレスにアクセスする。

## Firebase

### 初回だけ

```sh
cp .env.example .env.local   # .env.local はコミットしない
```

- 開発中は `.env.local` の `VITE_USE_EMULATOR=true` のままにする。ローカルのエミュレータに接続し、本番のデータには一切触れない
- エミュレータには Java 11 以上が必要（`java -version` で確認）
- 本番の Firebase につなぐときだけ、`.env.local` に Firebase コンソールの設定値を入れて `VITE_USE_EMULATOR=false` にする

### エミュレータ（Auth・Firestore）

```sh
npm run emulators   # 別のターミナルで起動したままにする
```

| 用途 | URL |
| --- | --- |
| 管理画面（ユーザーやデータの確認・削除） | http://127.0.0.1:4000 |
| Authentication | 127.0.0.1:9099 |
| Firestore | 127.0.0.1:8080 |

- プロジェクト ID は `demo-bukatsu`。`demo-` で始まる ID は本番の Firebase につながらない
- 終了時（`Ctrl+C`）にデータを `.emulator-data/` に保存し、次回の起動時に読み込む。消したいときはこのフォルダを削除する
- 同じ Wi-Fi のスマホからも接続できるよう、エミュレータは `0.0.0.0` で待ち受ける。アプリは開いたホスト名（PC の IP アドレス）のエミュレータにつなぐ
- 初回起動時に Firestore エミュレータ（約 140MB）をダウンロードする。回線が不安定で失敗したら、もう一度起動する

### モックと Firebase の切り替え

`.env.local` の `VITE_DATA_BACKEND` で接続先を選ぶ。

| 値 | 接続先 |
| --- | --- |
| `mock`（既定） | メモリ上のダミーデータ（`src/data/mock/`） |
| `firebase` | Firebase Auth と Firestore（`VITE_USE_EMULATOR=true` ならエミュレータ） |

ルールのテスト（`npm test`）やアカウントの扱いなど、Firebase 接続の詳細は [Firebase 接続ガイド](firebase.md) を参照。

### メールアドレスの確認（エミュレータ）

新規登録すると確認メールを送るが、エミュレータでは実際のメールは届かない。確認用のリンクは、エミュレータのログ（`npm run emulators` のターミナル）か、管理画面 http://127.0.0.1:4000/auth に表示される。リンクを開いてから、アプリの「確認しました」を押す。
以前に作ったエミュレータのアカウントは未確認のため、管理画面でメールを確認済みにするか、登録し直す。

### Google ログイン（エミュレータ）

エミュレータでは、本物の Google の画面の代わりにエミュレータのアカウント選択画面が開く。「Add new account」→「Auto-generate user information」→「Sign in with Google.com」で、架空の Google アカウントとしてログインできる。
本番で使うには、Firebase コンソールの「Authentication → ログイン方法」で Google を有効にしておく（#31）。

本番（Firebase Hosting）では、開いているサイトのドメイン（`bukatsu20261024.web.app`）でログイン処理を行い、Google のログイン画面にもそのアドレスが表示される（`src/data/firebase/app.ts`）。
このため Google Cloud コンソールの「API とサービス → 認証情報」で、Web クライアントの「承認済みのリダイレクト URI」に `https://bukatsu20261024.web.app/__/auth/handler` を登録している。
localhost から本番に接続するときは `.env.local` の `VITE_FIREBASE_AUTH_DOMAIN`（`firebaseapp.com`）を使う。

### コードからの使い方

`src/data/firebase/app.ts` の `auth` と `db` を使う。エミュレータへの接続や設定値の読み込みはこのファイルで済ませてある。

### セキュリティルール

`firestore.rules`（Issue #7）。方針は `docs/data-model.md`、検証方法は [Firebase 接続ガイド](firebase.md) を参照。本番への反映は `--project prod` を付けて行う。

## ディレクトリ構成

```
src/
  types.ts              … ドメインの型（docs/data-model.md と対応）
  data/
    repository.ts       … データ読み書きのインターフェース
    firebase/app.ts     … Firebase の初期化（auth・db を提供、エミュレータ接続）
    mock/               … モック実装と初期データ
    index.ts            … 使う実装の切り替え（Firestore 版はここで差し替える）
  app/                  … 起動・ログイン振り分け・タブ・共通の Context
  components/           … 画面をまたいで使う部品（ヘッダー、シート、ダイアログ、アイコン）
  features/
    auth/               … ログイン・新規登録・チーム参加／作成
    schedule/           … 予定タブ
    equipment/          … 用具タブ
    settings/           … 設定タブ
  lib/                  … 表示や並び替えなどの小さな関数
```

## 用具・設定・更新の確認（#9〜#11）

- 用具：空き優先・用具名順、ウィジェットの上限スクロール、複数用具の手放し、重複名拒否、編集・削除の確認、管理者の強制手放しを確認する。Issue #9のよみがなは後続の設計決定で廃止済みのため追加しない。
- 設定：表示名変更、参加コードの表示・コピー・LINE共有・再発行、予定の編集権限・種類、管理者の付与・解除を確認する。別の操作で名前や種類が変わった場合、未保存の入力を残し、最新値を明示的に読み直してから保存する。
- 更新：再取得中表示は固定の待ち時間ではなく各購読の初回通知まで。初回通知はキャッシュの場合もあり、サーバーへの同期完了を保証する表示ではない。エラーは別途トーストで通知する。
- 管理者が参加コードを表示した間だけコードを購読する。他の管理者が再発行すると表示と共有内容も変わる。
- 非表示中はデータ購読を停止し、復帰したときに張り直す。画面復帰と同じ状態のvisibilityイベントが続いても重複購読しない。

## 複数チームの確認

## Firebase の複数所属・削除の確認（#24）

`npm test` で複数所属、チーム別名前、旧プロフィール移行、除名時の他所属保持、削除途中からの再開、メモ100件超の清掃、直接SDKからの不正な所属更新・削除ロック回避の拒否を検証する。本番へ接続せず `demo-bukatsu` のエミュレータのみ使用する。

手動確認は2アカウントで2チームに参加し、表示名を別々に変更する。片方だけを離脱／除名して他方が残ることを確認する。削除を途中で止めた場合、開始者が対象チームを開いて「削除を再開」を押す。他チームは上部から切り替えられる。古いルールでは新しい所属更新が拒否されるため、アプリとルールの本番反映は同時に行う（このIssueの作業はPRまで）。

## 複数タブでの認証保持（#64）

Auth・FirestoreエミュレータとFirebase版の開発サーバーで、同じブラウザ・同じオリジンの通常タブを2つ使用する。別のプライベートセッションは使わない。

1. メール／パスワードで新規登録し、確認メールの案内画面を表示したまま同じURLを2つ目のタブで開く。両方でログイン状態が残ることを確認する。
2. ログアウトしてからメール／パスワードでログインし、新しいタブを開いて同様に確認する。両方を再読み込みしても保持されることを確認する。
3. GoogleログインではAuthエミュレータのテスト用ポップアップを使い、架空のGoogleアカウントでログインする。同じURLを新しいタブで開き、両方でチーム参加画面が維持されることを確認する。実Googleの認証情報は使わない。
4. 片方でログアウトするともう片方もログアウトすることを確認する。

Node.jsのエミュレータ統合テストはブラウザのIndexedDB／localStorage間の移行を再現しないため、上記の実ブラウザ確認も必要。保存先を個別のログイン処理で変更しない。

ポップアップを操作できない自動操作環境では、Vite起動後に `/tests/browser/auth-persistence.html` を2タブで開く。これは本番ビルドに含まれないlocalhost専用の確認ページで、通常と同じ `getAuth` とリポジトリを使用する。Googleのみエミュレータの資格情報へ差し替える（実Googleポップアップの動作検証とは区別する）。各ログイン後に2つ目のタブを開き、1つ目の「通知履歴」に意図しない「ログアウト中」が増えないことを確認する。メールとGoogleの両方で、再読み込みによる保持と明示的なログアウトの同期も確認する。

## 大量データの検証（#69）

Node.js24とJava21以上で `npm run scale:check`。専用の `demo-bukatsu-scale` と別ポート（Firestore18080/Auth19099）を使用し、既存の開発エミュレータや本番に接続しない。検証後に `.scale-artifacts/` へ計測結果・ブラウザ用fixture・エミュレータexportを保存する。約10万件のメモを扱い、単発の実行で数分かかるため、通常の `npm test` とCIでは負荷テストをスキップする。

`npm run scale:seed -- demo` または `large` は専用エミュレータへの投入だけを行う。手順・Safari画面確認・既知の制約は [大量データ検証記録](performance/issue-69.md)を参照する。生成した架空アカウント情報やexportはgit管理しない。実アカウントのメールや本番データをfixtureへ転記しない。
